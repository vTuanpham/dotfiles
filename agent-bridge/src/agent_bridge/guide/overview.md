# agent-bridge workflow

One CLI with four backends: `codex`, `agy`, `claude` and `opencode`.

## Which backend
- **Never bridge to your own harness.** A Claude root uses its Agent tool for Claude workers, a Codex root its own subagents, an agy root its own. The bridge is only for the other harnesses.
- Before launching, read the notes of the backend you will launch in `agent-bridge start --help`: its models, effort levels, quota and quirks.
- No backend is the default. Use the delegation and model-selection skills for task/model choice; read only the selected backend's execution notes here.
- A delegated worker never starts jobs itself; the runner tells every worker so.

## Model references

Use the model-selection skill for model choices. `model-guide read maintenance`
owns reference updates; `model-guide check` reports drift without changing files.

## Jobs
- Flags are in `agent-bridge <command> --help`.
- Use a short owner tag (project + topic) unique to this session; sessions share job storage. Never use `/tmp` for job data.
- Prepare a clear brief before starting a job. Reviewers need network for docs, API contracts and test scratch: start them workspace-write with `--writable-root <job>/out`, brief "don't edit the repo; scratch only under <job>/out", and check `git status` afterwards.
- Approvals are auto-declined. Never bypass a backend's sandbox.
- Worker environments drop secret-like names by default. Set `AGENT_BRIDGE_PASS_ENV=NAME1,NAME2` before launch to opt specific names in; `AGENT_BRIDGE_DENY_ENV` adds exact denied names and wins conflicts. Backend auth files/config paths, ordinary runtime and proxy settings remain available. See the README's Worker environment section for matching rules and limits.
- Every job runs in a systemd user scope inside `codex.slice`. `start ... --memory 4G --cpu 400%` chooses that job's caps; `resume <job> --memory 5G --cpu 400%` applies caps on the next runner launch. Defaults remain `CODEX_JOB_MEMORY_MAX` (2500M) and `CODEX_JOB_CPU_QUOTA` (300%). Explicit and default caps are checked against effective slice/host limits and refused above them. `owners` and `watch` show each job's caps. Missing CPU controllers mean configured CPU quotas may not be enforced. Check actual memory/CPU budgets before choosing concurrency; brief data-heavy agents to stream or chunk.
- Use `agent-resources run --mem SIZE -- <command>` for heavy foreground work; its own `guide` owns admission, controls and limits. Bridge injects job/controller identity and worker restrictions. Resource waits appear in Bridge status and do not wake the root.

## Watch and wait
- Choose a group policy when launching several workers: `group set OWNER NAME --wake each|all|quiet`, then `start ... --group NAME` (or `resume --group`, `group assign OWNER/JOB NAME`). Default `each` coalesces completions for 60 seconds; `--settle 0s` gives immediate wakes. `all` waits for every member; predeclare `--members a b` before launch and use `--max-wait 30m` for a partial digest naming missing jobs. `quiet` keeps completions visible without waking. Unassigned jobs share their owner's default group. `group list OWNER` shows policies; `group clear OWNER NAME` restores defaults.
- Failures, questions, errors/declined approvals, URGENT/BLOCKING messages, retry exhaustion and observed job OOMs wake immediately and flush held results. Unread completions wake the root once after 15 minutes by default, including under `quiet`, in every harness with an armed watch; choose `--remind 20m` or `--remind off`, and opt into repeat backoff with `--repeat-reminders`. Reminder wakes do not require `--include-info`; that flag does not bypass group policies. Routine messages and slow/stall notices retain opt-in behavior; heavy waits and retries never wake.
- The shared [stall classifier](status.md#bounded-waits-and-one-stall-classifier-v12) owns silence, command and wait grace. Use `waiting --on command|peer|root|external|dependency --for 20m --note 'short reason'` before a long silent wait; add `--peer NAME` for a sibling. The next tool call or message clears it. Heavy-slot waits, pauses and retries are known states. Long commands and overdue declarations are informational only, including with `--include-info`; ordinary slow/stall notices retain opt-in behavior. `--stall-min` overrides the classifier's silence threshold.
- The runner injects the URGENT/info rule into every worker, so briefs needn't repeat it.
- Watch covers the selected owner directories and picks up new jobs while it runs.
- Launch with `start ... --watch`, `resume ... --watch`, or `steer <job> "message" --watch` as a background command of your harness. Start and resume run detached; steer resumes an idle job detached or uses its existing runner. Then the command wakes on the first urgent event, so one command covers launch or enqueue. `--watch SECONDS` (default 1800) bounds the initial wait; a Codex watch may stay alive past it while a reminder/group schedule is pending. When steering, put text before `--watch` or use `--watch=SECONDS` before the text. `--prompt-file` also avoids positional ambiguity. Exit 124 means the initial timeout passed with the worker still running. Keep bridge calls plain so harness allow rules match them.
- Watch replays unacknowledged critical events and follows live work. Completion digests wake once per batch, including across re-armed watches; results stay unread until explicit `result`/`ack`. Printing a digest marks its referenced results displayed, not acknowledged. `ack OWNER` (or `OWNER/JOB`) acknowledges only displayed events; `result JOB` acknowledges only completions read before that call. New arrivals stay pending. Reminders clear when their results are acknowledged.
- Re-arm with `agent-bridge watch <owner> --until-event --timeout 1800` in a background terminal; several jobs or owners can share a watch. Pending events replay even if no jobs are running. Codex keeps its current native watch alive through scheduled reminders and group completions; re-arm after an event if a job remains but no schedule does. Other harnesses must re-arm while a schedule remains. Acknowledging results or setting `--remind off` removes the reminder schedule. Reminders are observation-driven: without an armed watch, nothing sends a background reminder. No separate result/log sweep after arming is needed. Watching alone never starts work.
- Owner tags are root namespaces: use a unique owner for each root. Cursors live in `$AGENT_BRIDGE_HOME/jobs/<owner>/ack.json` (default `~/.local/state/agent-bridge/jobs/<owner>/ack.json`), version 1 with `jobs` keyed by job name. Each cursor stores log identity `log` (`device:inode`) and byte offsets `through` (explicitly acknowledged), `seen` (displayed), and `completed` (completions acknowledged by result). Owner locking and atomic writes protect concurrent watches/results. Missing cursors replay existing urgent history; replaced or shortened logs reset that job's cursor. Old jobs need no migration.
- To transfer an existing owner namespace to a different known root, run `agent-bridge handoff OWNER` from the new root first. The transfer is locked; afterwards, commands and watches from the previous known root cannot mutate, acknowledge or deliver that owner's jobs. Unknown/rootless sessions keep legacy access without replacing a known binding.
- Use detached launches and an armed Bridge watch when applying group wake policies.
- Keep doing your own work while workers run; prefer background waits. If one runs longer than its task warrants or goes quiet, read `tail <job>/live.jsonl` and `<backend>.stderr.log` early, then steer it, stop it, or take over.
- If a blocking wait is necessary, use a timeout of at least 180 seconds, subject to harness limits. Tool yield intervals are separate from command timeouts. Avoid foreground sleeps and short polling. Use Bridge's stop/interrupt/watch controls for its jobs; shared shell matching guidance lives in `~/dotfiles-with-agency/shell/README.md#agent-process-matching`.

## Steer, resume, peers
- **Steer**: `agent-bridge steer <owner>/<name> "message"` delivers to the existing runner, or resumes an idle job detached in the same session and sandbox. Delivery during a turn depends on the backend. The runner also checks for late steers before exiting, so a finishing turn cannot strand a follow-up. Add `--watch` to follow it in the same background command. Use `--queue` to queue without starting an idle job, then `resume` once to deliver the batch in order (`--queue` and `--watch` are mutually exclusive). A live runner may still consume queued messages. Retired jobs require `restore` first; watching alone never starts work.
- **Questions**: steering a live runner awaiting an answer keeps that runner and its pending question. For Codex native questions, answer through `<job>/inbox/<requestId>.md`; a steer is a follow-up, not a native question answer.
- **Interrupt and stop**: interrupt ends the current turn; stop ends the runner.
- **Resume**: keeps the same native session, context and sandbox. Without a prompt file, queued steers take precedence; with nothing queued, it sends only `Continue.`. After a failed/ended turn, `agent-bridge resume <job> --model M --effort E` continues the original thread on that model, without a recap or new job. For writes after a read-only audit, start a fresh workspace-write job; never edit `state.json`.
- **Transient failures**: the runner retries server overload/capacity, retryable rate limits and matching 429/502/503/504 failures up to four times in the same native session/model, sending only `Continue.` (queued steers still win). Jittered exponential backoff totals 165–330 seconds over all four waits. Attempts appear in status/log, without wake-ups; exhaustion emits one urgent failure stating the retry count and suggesting `resume <job> --model M` for the SAME thread. Authentication, billing/account quota, context/model errors and unknown errors are not retried. No native session means no automatic continuation. Stop/interrupt can cancel backoff. See the failure classification notes in retries.md.
- **Compact**: `agent-bridge compact <owner>/<name>` supports idle codex and claude jobs only. Claude reports a no-op when there is too little history; compaction leaves queued steers for a later resume.
- **Peers**: workers under the same owner message each other. An agent message starting `TO <job>[, <job>]: ` queues a steer for that job's runner; peer messages do not start idle jobs. Name peers and their file ownership in each brief, so cross-area requests go worker-to-worker. Plain messages already reach root as info; `TO root`, `TO coordinator` or `TO <owner>` are treated the same way, not as unknown peers. A worker that needs root to act now starts its message with `URGENT:`.
- **Takeover**: watch, steer or resume another owner's jobs only when the user asks; find them with `owners` and use the full `<owner>/<name>`.
- **Reporting**: brief agents to message only for blockers, questions, concrete checkpoints (edits done plus check results) and the final report. Relay to the user only those checkpoints and the final results.

## Briefing and verification

The delegation skill owns shared briefing, task division and review guidance.
Bridge workers already load global/project instructions. Give them routed docs,
file ownership and checks, and preserve their sandbox. Root performs Git writes
outside a worker's sandbox; tool access never grants commit or publication authority.

## Worktrees
- Writers each get their own git worktree and branch (`git worktree add ../<repo>-<name> -b <name> main`). Sandboxed workers can't write a worktree's git metadata, so root does all commits and rebases.
- Merge the reviewed branches, then remove the worktrees. Cap concurrent test-running writers to what the host can take; read-only reviewers are light.

## Cleanup (root's job, never the user's)
- Keep jobs available for related follow-ups, verification and review. Retire only when the work is resolved and you are confident its context is no longer needed; a completed turn, saved report or merged result alone is not enough.
- Run `agent-bridge retire <owner>/<name>` once that condition holds. Retirement archives its prompt head and final report, hides it from active listings/watch/sessions, and records `retiredAt` and `purgeAfter` in its state. The job directory, backend homes, session IDs and worktrees stay in place.
- Retirement is reversible until the data is purged: `agent-bridge restore <owner>/<name>`, then `agent-bridge resume <owner>/<name>` continues the same native thread/session. Passing the purge date alone does not delete data, so restore still works until purge actually runs.
- The default retention is 14 days from retirement. Set it for a job with `retire <owner>/<name> --keep-days N` (positive whole days). Repeating retire does not reset its date; restore and retire again to set a new window.
- `agent-bridge purge` explicitly deletes all retired jobs past their recorded purge date; `purge <owner>/<name>` targets just one eligible job. Nothing purges automatically. Wake's tidy scan counts only expired retired jobs, excluding dirty worktrees and live runners, and asks the root to use `purge`. Purge removes clean `out/wt` git worktrees without force and refuses dirty/unreadable worktrees or live runners.
- For immediate disk recovery, `retire <owner>/<name> --purge` archives and permanently deletes that job, bypassing retention. Restore cannot recover purged data. `result <owner>/<name>` still reads the live report while retained, or the archived final report after purge (including older archives); archives contain only the prompt head and up to 2,000 report characters, not native sessions or full transcripts.
- At the end of a session, review finished work before retiring it; age alone is not a reason to retire. Keep worktrees needed for follow-ups. List dirty worktrees or anything still running for the user's OK; never force-delete them.
